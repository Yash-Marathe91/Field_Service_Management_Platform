01   Project Overview 
 
KEYSTONE is the field-service platform Meridian Facilities Management uses to run its 
maintenance operation — from the moment a customer reports a problem to the moment the 
job is closed and billed. You are building it end to end: a Spring Boot back end, a React front 
end, and a PostgreSQL database behind them. 
Meridian sends technicians to commercial buildings to service HVAC, electrical, and plumbing 
systems. Today that work is coordinated with spreadsheets, phone calls, and messaging apps. Jobs 
get lost, technicians arrive without the right information, and managers cannot see what is overdue. 
KEYSTONE replaces that with one system: dispatchers raise and assign work orders, technicians 
update them from the field, managers watch SLAs and dashboards, and customers can log requests 
and track progress. 
 
Figure 1.  KEYSTONE takes every inbound request through to a closed, accounted-for job. 
1.1  What you are building 
A single platform with four kinds of user — dispatcher, technician, manager, and customer — each 
seeing only what their role needs. Behind it sits a clean layered Spring Boot service with a governed 
work-order lifecycle, role-based security, parts and time tracking, SLA monitoring, and reporting. The 
full feature list and acceptance criteria are in Section 09. 
What good looks like 
A dispatcher can raise a work order, assign it to the right technician, and see it move across a board. 
A technician can open their jobs on a phone, start work, log parts and time, and mark it complete. 
A manager can see what is overdue, who is overloaded, and whether the team is hitting its SLAs. 
A customer can raise a request and watch its status without phoning anyone.

03   User Roles & Access 
 
KEYSTONE has four roles. Access is enforced on the server for every request — the UI hiding a 
button is never the security boundary. Role checks live in the service/controller layer.

Dispatcher Create customers, sites, and work orders; assign work orders to technicians; see all 
jobs and the board. 
Technician See work orders assigned to them; start, hold, and complete jobs; log parts and time; 
upload photos. 
Manager / Admin Everything a dispatcher can do, plus close jobs, manage users and parts, and view all

3.1  Access rules 
• Every endpoint is authenticated; anonymous access is limited to login and customer request 
submission where allowed. 
• A customer can only ever see data for their own organisation’s sites and work orders — never 
another customer’s. 
• A technician can only act on work orders assigned to them; they cannot reassign or close jobs. 
• Destructive and administrative actions (user management, parts, close-out) are restricted to 
Manager / Admin. 
Authorisation is server-side, always 
Hiding a control in the React app is a usability choice, not a security control. Every protected action must be 
re-checked on the server with Spring Security (method-level @PreAuthorize or equivalent). Assume a 
determined user will call your API directly.

Integrity rules 
A work order must always belong to a customer and a site. Status changes are append-only in the history 
table (never edited or deleted). Using parts on a job and decrementing stock must happen in one 
transaction — partial updates are not allowed. 
06   System Architecture 
 
KEYSTONE is a classic layered Spring Boot application behind a React SPA. Requests flow from 
the browser to controllers, into services that hold the business rules, down to JPA repositories and 
PostgreSQL. Keep the layers clean: controllers stay thin, business logic lives in services, and 
entities never leak directly to the client — map to DTOs. 
 
Figure 3.  System architecture — a React SPA over a layered Spring Boot service and a PostgreSQL database. 
6.1  Layer responsibilities 
Layer Responsibility 
Controllers HTTP only: validate input, enforce auth, map DTOs, delegate to services. No 
business logic. 
Services Business rules, the work-order state machine, SLA logic; transactional 
boundaries (@Transactional).

Layer Responsibility 
Repositories Spring Data JPA data access; queries scoped so customers only read their own 
data. 
Persistence PostgreSQL with Flyway-managed migrations; no schema changes by hand. 
6.2  Principles 
• Thin controllers, rich services: business decisions live in one place and are testable. 
• DTOs at the boundary: never serialise JPA entities straight to the client. 
• Transactions guard invariants: multi-step changes (status + history + stock) commit together or 
not at all. 
• Migrations, not magic: every schema change is a reviewed Flyway script, runnable on a clean 
database. 
07   Work-Order Lifecycle 
 
The work-order lifecycle is the core business rule of the platform. A work order moves through a 
fixed set of states, and only certain transitions are allowed. Enforce this in the service layer — not 
just in the UI — and write an audit row on every change. 
 
Figure 4.  The governed work-order lifecycle. Illegal transitions are rejected; every change is recorded. 
7.1  States 
State Meaning 
NEW Raised but not yet assigned to a technician. 
ASSIGNED Allocated to a technician, not yet started. 
IN_PROGRESS The technician is actively working the job. 
ON_HOLD Paused (e.g. waiting on parts or access).

State Meaning 
COMPLETED Work finished, awaiting manager / customer sign-off. 
CLOSED Signed off and accounted for — terminal. 
CANCELLED Abandoned before completion — terminal. 
7.2  Rules 
• Only the transitions shown in the diagram are permitted; any other change is rejected with a 
clear error. 
• Each transition is restricted by role (e.g. only a manager can CLOSE; only the assigned 
technician can start). 
• Every transition writes a WorkOrderStatusHistory row: from, to, who, when, and an optional 
note. 
• Terminal states (CLOSED, CANCELLED) cannot transition further. 
08   Security & Authentication 
 
Security is a first-class requirement, not an afterthought. KEYSTONE uses stateless JWT 
authentication with Spring Security: users log in once, receive a signed token, and present it on 
every request. The server holds no session. 
 
Figure 5.  Stateless authentication: log in, receive a signed token, and prove identity and role on every request. 
8.1  Requirements 
• Passwords are stored only as BCrypt hashes — never in plain text or reversible form. 
• JWTs are signed with a server secret and expire; expired or tampered tokens are rejected. 
• Every protected endpoint enforces role with Spring Security (method-level authorisation). 
• Sensitive values (DB credentials, JWT secret) come from configuration/environment, never 
hard-coded or committed. 
• Input is validated on the server (Bean Validation); errors return a consistent, structured 
response.

10   API Design 
 
Design the REST API to be predictable and conventional. Use nouns for resources, proper HTTP 
verbs and status codes, consistent error responses, and pagination on list endpoints. A 
representative slice is below; the full reference is in Appendix B. 
Endpoint Method Purpose 
/api/auth/login POST Authenticate; returns a JWT. 
/api/work-orders GET List work orders (filterable, paginated, role-scoped). 
/api/work-orders POST Create a work order. 
/api/work-orders/{id} GET Fetch one work order with its history. 
/api/work-orders/{id}/assign POST Assign to a technician. 
/api/work-orders/{id}/status POST Transition status (validated against the lifecycle). 
/api/work-orders/{id}/parts POST Log parts used (transactional). 
/api/reports/summary GET Dashboard metrics. 
10.1  Conventions 
• Status codes mean what they say: 200/201 success, 400 validation, 401/403 auth, 404 missing, 
409 illegal transition. 
• Errors return a consistent JSON shape (timestamp, status, message, field errors) — never a 
stack trace. 
• List endpoints support pagination, sorting, and filtering; never return unbounded result sets. 
• The whole API is documented with OpenAPI/Swagger and browsable.

20   Appendix A — Domain Glossary 
 
Term Meaning 
Work order A unit of maintenance work: what needs doing, where, for whom, by when. 
Dispatcher The person who raises and assigns work orders to technicians. 
Technician The field engineer who performs the work and updates the job. 
Site A specific building/location belonging to a customer. 
Asset A piece of equipment at a site (e.g. an HVAC unit) that work relates to. 
SLA Service-Level Agreement — the response/resolution time the job must meet. 
Status history The append-only record of every state change on a work order. 
Lead time Used for stock: time between ordering a part and it being available.
